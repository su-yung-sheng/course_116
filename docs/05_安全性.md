# 05 安全性：不讓 F12 看到答案

> 目標：學生按 F12（開發人員工具）翻原始碼、網路請求、`window` 變數，**都看不到明碼答案**；
> 想用程式一個一個試，也要付出代價。
> 這是「前端能做的」版本。真正做到「答案完全不在學生電腦上」，要等後端評分（見最後一節）。

## 一、做法總覽

```
private/（明碼，只在老師電腦）  ──  node tools/build.mjs  ──►  公開檔案（封存版，進 Git、放上 GitHub Pages）
```

| 內容 | 以前（F12 看得到） | 現在 | 對了怎麼知道？ |
|---|---|---|---|
| 互動遊戲 分類題（sort） | `a: '作業系統'` | 每個選項一個雜湊 | 學生按的那一格算雜湊，和關卡裡的比對 |
| 互動遊戲 排序題（order） | 題目就是正確順序 | 題目先打亂；每一步存雜湊 | 每按一顆算一次「到目前為止的順序」 |
| 互動遊戲 組合題（build） | `ok: true` | 雜湊 | 同上 |
| 互動遊戲 打字題（type） | `a: ['BYTE']` | 雜湊（先轉半形、大寫、去空白） | 學生打的字算雜湊 |

| 🎲 隨機出題（密碼特務、網路世界的操作／挑戰階） | —— | **沒有答案清單**：題目當場亂數產生 | 照規則把答案算出來比對（例如 IP 是不是私有、封包少了哪幾號） |

錯了**不公布正解**：遊戲扣一顆心、同一題再答；5016B 顯示模擬器結果，請學生再預測一次。

## 二、技術細節（`shared/seal.js`）

- `SEAL.h(salt, 值)`：SHA-256(`salt|值`) 取前 24 個十六進位字。每一題的 salt 都不一樣（由 `private/pepper.txt` ＋ 題目位置算出），所以不能拿別題的雜湊對照，也不能事先建表。
- `SEAL.seal / open`：PBKDF2（20000 次）把「正確答案」變成 AES-GCM 金鑰。**打開一次約要幾十毫秒**，拿程式亂試會明顯變慢；打不開就是錯。
- `SEAL.obscure / reveal`：只是混淆，給「一定要在瀏覽器裡用到」的東西（隱藏測資輸入、提示）。

## 三、做不到的事（誠實說明）

1. **選項少的題目還是能硬試**：二選一、四選一的題目，學生本來就可以每個都按按看；前端能做的只是不讓他「不用試就知道」。遊戲用愛心限制次數，這才是真正的防線。
2. **Python 隱藏測資的輸入只是混淆**：評分時一定要把輸入交給 Pyodide 執行，所以懂 JavaScript 的學生在主控台下斷點還是看得到。但他仍然要寫出能通過的程式 —— 看到輸入不等於拿到答案。
3. **星星存在 localStorage**：懂的學生可以在主控台改自己的星星。要防這個，只能讓伺服器記分。
4. **Git 歷史**：這個機制加入前推上 GitHub 的版本還是明碼。要清掉必須改寫歷史（`git filter-repo` ＋ force push）或開新 repo。

## 四、之後：後端評分（真正的解法）

| 方案 | 做法 | 優點 | 代價 |
|---|---|---|---|
| Firebase Cloud Functions（建議） | 學生送出 → 函式在伺服器比對答案、寫星星到 Firestore | 答案與記分都不在學生電腦；和 course_115 的 Firestore 同一套 | 要開 Blaze 方案（用量小通常免費） |
| Google Apps Script | 試算表當資料庫，doPost 評分 | 免費、學校帳號就能用 | 慢（每次 1～2 秒）、Python 評分做不到 |

Python 評分在伺服器跑需要沙箱（例如 Cloud Run 上的 Pyodide 或受限的 Python），比較複雜；可以先把遊戲、試算表、5016B、快速檢核搬到後端，Python 仍在瀏覽器跑、只把「結果」送去伺服器驗證雜湊。

## 五、老師要做的事

1. **備份 `private/`**（隨身碟＋雲端硬碟）。它不在 GitHub 上，電腦壞了就沒了。`pepper.txt` 換了，所有封存都要重新建置。
2. 改題目 → 改 `private/` → `node tools/build.mjs` → `cd tests && npm test`（第一步 `leak_scan` 會檢查有沒有明碼漏出）→ 推送。
3. 公開的 `content/*.js` 開頭有「⚠️ 自動產生」字樣，**不要直接改**。
